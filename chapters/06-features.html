Chapter 6 · Part II · Data

Features

In which I teach a robot that food ads do better at lunchtime, and accidentally let it read the answer key.

Here's a slightly humbling fact about the model you're about to train in Chapter 7. It's a logistic regression, and all it does is add up some weights, one per feature, and squash the total into a probability. That's it. That's the whole trick.

Which means that whatever patterns exist in how Pebble's users click, the model can only find them if some feature, or some combination of features, points right at them. The model can't see what you don't show it. So this chapter is about building those features, and honestly, it's the part of modeling where your product intuition is worth the most. Finally, a chapter where "I know our users" is a technical skill!

6.1The kinds of features

Features come in a few flavors. Here's the menu, with Pebble examples:

KindExamples on PebbleWhat it captures
ID (sparse categorical)ad=182, adv=17, user=517Anything specific to that one entity: an ad's appeal, a user's click habits
Categorical contextdevice=android, hour=21, country=BRSituation-level effects
Crossage×cat=0_9 (18–24 × Gaming), hour×cat=12_10 (noon × Food)Effects that exist only for a combination
Sequence / historycategories of the last 12 engaged postsCurrent and long-term interests
Counting (statistical)the ad's CTR so far; the user's CTR so farDense summaries of past behaviour; they generalize across IDs
Dense / embeddinga learned 16-number vector per user (Ch. 10–11)Similarity: users and ads that behave alike end up close

Your stack's logistic regression uses binary features. Each feature is a string like "hour×cat=12_10". It's either present or it isn't, and the model learns one weight per string. The prediction is the sigmoid of the sum of the weights of whichever features are present:

\[ \hat p = \sigma\Big(\sum_{f \in \text{features}(x)} w_f\Big), \qquad \sigma(z) = \frac{1}{1+e^{-z}} \]

6.2The hashing trick

Quick question: how many distinct feature strings are there? For users and ads alone, as many as there are users and ads, and new ones show up every single minute. Keeping a giant dictionary from string to weight, and updating it constantly, is a pain.

So production systems do something delightfully lazy. They hash each string into one of \(B\) buckets and keep a fixed-size weight table. New strings just… work. No dictionary updates needed. The price you pay is collisions: two completely unrelated features that land in the same bucket have to share a weight, like strangers forced to share an Uber.

How big should the table be?
The distinct feature strings in your logs, hashed into tables of different sizes. Then the same logistic regression is trained with each table size.

A production model has an embedding table for user IDs: 50 million rows, 64 numbers per row, 4 bytes per number. How big is the table in gigabytes (10⁹ bytes)?

Hint

50,000,000 × 64 × 4 bytes.

50M × 64 × 4 = 12.8 × 10⁹ bytes = 12.8 GB. For one feature's table. That's why ID features dominate the memory (and the cost) of big recommender models, why hashing and pruning matter so much, and why "let's just add an ID feature for X" is actually an infrastructure request wearing a modeling costume.

6.3Counting features and smoothing

An ID feature learns an ad's appeal slowly, one gradient step at a time. A counting feature skips the wait and hands the model a summary directly: "this ad's CTR so far is 4%." Counting features also work for brand-new IDs as soon as a little data trickles in, no retraining required.

But raw ratios get silly when counts are small. An ad with 1 click in 3 impressions does not have a 33% CTR, no matter how much its advertiser wants to believe it. The standard fix is to smooth the ratio toward a prior, as if you'd already seen a few extra impressions at the average rate:

\[ \widetilde{\text{CTR}} = \frac{\text{clicks} + \text{prior} \cdot m}{\text{impressions} + m} \]

Here \(m\), the strength, is how many imaginary impressions the prior is worth. Watch one ad's estimate settle down as its impressions roll in:

6.4Crosses

Remember how logistic regression just adds things up? That has a funny consequence. Give it separate features hour=12 and cat=Food, and it can learn "noon is a little better for everyone" and "people click Food ads a lot." What it can't learn is "Food ads do especially well at lunchtime," because that effect only exists for the combination. So we build the combination ourselves. A feature cross turns it into a feature of its own: hour×cat=12_Food gets its very own weight.

Pebble's world is full of these interactions: food at mealtimes, gaming late at night, finance on iOS, and category tastes that shift with age. Crosses let a humble linear model capture them. The catch is that they multiply. Crossing a 24-value feature with a 12-value feature makes 288 new features, and crossing IDs with IDs explodes completely. For years, choosing which crosses to build was basically the job of ranking engineers. Chapter 11's cross layers and attention are ways to learn the useful interactions instead of hand-picking them.

6.6Leakage: the feature that knows the answer

Okay, remember that "never reach for anything later" rule? Here's why it matters.

A leaky feature contains information about the label that won't exist at serve time. The classic ads example is a counting feature computed over a window that includes the impression's own outcome. Take a per-user CTR feature. Computed properly, it only uses the user's clicks before the day of the impression. Computed carelessly, after the fact, over all ten days, it includes this very row's click. For a user with 30 impressions, one click moves their CTR a lot. So the model learns to read the answer straight off the feature. It's basically cheating on the test, and it's really good at it.

A leak, measured
Your features plus a user-CTR feature, computed two ways. "Offline" evaluates each model the way it was built; "online" uses what serving would actually have.
Common trap

An offline gain that looks too good to be true. If a new feature pushes AUC past what anyone thought was possible (here, close to or even above the oracle), assume it's a leak until someone proves otherwise. Ask three questions. When exactly is this feature computed, relative to the impression? Would its value be the same if we computed it at serve time? Does it aggregate over a window that overlaps the label's window?

Which of these proposed features leaks the label for a pCTR model?

  • Number of ads the user clicked in the previous 7 days, as of the request
  • The hour of day of the request
  • The user's session length for the session containing the impression, from the session log
  • The ad's category

Session length is only known when the session ends, after the ad was already shown. And clicking an ad changes the session (the user leaves the app, or sticks around longer). So the feature is correlated with the label for reasons that won't exist at serve time. It'd look amazing offline, and be unavailable, or just different, in production.

You shrink the hashed weight table from 2²⁰ to 2¹² buckets to save memory, and AUC drops. What's the mechanism?

  • Features are dropped when the table is full
  • Unrelated features share buckets and have to share one weight
  • The model has fewer layers
  • The learning rate becomes too high

Fewer buckets, more collisions, more strangers sharing an Uber. A single weight might have to serve a user ID and an hour×category cross at the same time, and the model can't tell them apart. Frequent features dominate the shared weight, and the rare ones just get noise.

A data scientist proposes adding "advertiser's total spend last 30 days" as a feature, and it gives +0.8% AUC offline. You're the PM. What do you want to know before it ships?

  • Leakage and timing. Is spend computed as of the impression, with a lag matching how fresh it'll be in serving? Spend is literally the sum of clicks × prices, so a window that overlaps the label period leaks clicks.
  • Serve-time availability and freshness. Can serving fetch it within the latency budget, and how stale will it be? A daily batch? Then train it with the same staleness.
  • Fairness to advertisers, and incentives. This feature makes big spenders look more clickable. Is that real signal (brand strength), or a rich-get-richer loop where spend buys delivery, which buys more spend? Check calibration for small vs. large advertisers, and for new advertisers with zero spend.
  • Ablation against what's already there. Does it add anything beyond the advertiser ID and counting features, or is it just repeating them?
  • Online test. Offline AUC gains from features like this often shrink online. Require an A/B test with per-advertiser-tier metrics.
